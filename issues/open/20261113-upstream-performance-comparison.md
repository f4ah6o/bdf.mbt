# 上流と同等機能の Wasm 配信サイズ・処理時間・メモリ使用量を比較して併記する

Status: open
Model: unknown
Created: 2026-11-13
Updated: 2026-11-13
Branch: research/20261113-upstream-performance-comparison

## 概要

PDF・DOCX・PPTX の同じ変換機能を含む上流 Go 版と bdf.mbt のビルドを固定し、Wasm 生サイズ・gzip・Brotli・初回ロード総量、処理時間とメモリフットプリントを再現可能な条件で計測して併記する。
まず機能・実行経路の対応と測定可能性を確定し、比較不能な指標を無理に数値化しない。

## 背景

- 比較対象は [shibukawa/bdf](https://github.com/shibukawa/bdf) と本リポジトリ。両方の commit SHA、toolchain、依存バージョンを測定時に固定する。
- 本リポジトリの `moon.mod` は js、wasm-gc、native を対象とし、優先 target は js。README は PDF subset、DOCX、PPTX の対応と制約を記載している。
- Wasm 単体の大きさは、Worker、JS glue、ランタイム、必要な補助資産を含む利用者の初回ロード総量とは異なる。
- 既存の XLSX fixture 容量削減 issue はテストデータの保存量を扱うもので、本件の配信・実行性能比較とは区別する。

## 問題

機能の有無、入力、フォント、起動経路、キャッシュ、メモリ測定範囲が揃わない数値を並べると誤解を招く。
同じ PDF・DOCX・PPTX 変換を含むビルドの配信量と実行時コストを、条件付きで比較できる結果が必要である。

## 目標

機能対応表・測定手順・生の測定値・集計表を用意し、上流と bdf.mbt の結果を README または比較ドキュメントへ併記する。
既存の紹介ページから結果を参照できるようにする。

## 対象外

- 比較結果の優劣を先に決めること、測定のためだけに片側の機能を削ること。
- 本件だけで PDF/DOCX/PPTX 全機能の完全互換を実現すること。
- native Go とブラウザー Wasm を同じ実行条件として混ぜること。
- KiCad・基板・楽譜・EPUB、非公開・個人情報を含む入力。
- 絶対値を環境非依存の性能保証や公開 CI の合否閾値として使うこと。

## 提案する方針

1. 同一変換（入力形式、出力形式、オプション、対応機能）の対応表を作り、PDF・DOCX・PPTX をすべて含む実際のビルド構成を固定する。片側の未対応機能と外部ランタイム・フォント依存は明示する。全機能が揃わなければ共通 subset と現行配布版の比較を分ける。
2. release/最適化フラグ、デバッグ情報、source map、全 Wasm module の SHA256 とバイト数を記録する。同じ圧縮ツール・版・パラメータで raw/gzip/Brotli を測る。
3. 初回ロードはキャッシュと Service Worker を空にした同じブラウザーで、起動から最初の変換結果が利用可能になるまでに必要な資産を計上する。Wasm、JS/glue/Worker、フォント等の内訳、遅延ロード、転送圧縮方式、入力文書の扱いを明記し、合計との一致を検証する。ネットワーク転送量と展開後サイズを別列にする。
4. 公開または合成の共通入力を小・中・大、文字/画像/複数ページの代表ケースで固定する。出力の成功と意味・描画上の妥当性を先に検証し、未対応や失敗を高速化として集計しない。
5. 同一マシン・OS・ブラウザーで cold start（読込・コンパイル・初期化）と warm 変換を分ける。開始/終了点（I/O、転送、描画を含むか）を定義し、warm-up、反復回数、中央値、ばらつきを記録する。p95 を出す場合は十分なサンプル数と定義を併記する。
6. メモリは起動後 baseline、変換中 peak、終了後 retained を測る。Wasm linear memory、JS/GC heap、Worker を含むプロセス RSS/PSS など取得できる指標と範囲を区別し、Wasm GC の値を linear-memory サイズと同一視しない。ブラウザー API の制約や取得不能は N/A とし、代替値はラベルを分ける。
7. コマンド、入力ハッシュ、測定環境、ビルド構成、圧縮設定、計測 raw data と集計方法を保存し、別実行で再現できる比較表を公開する。大きい生成物は Git に埋め込まず再生成手順を残す。

## 受け入れ条件

- [ ] PDF・DOCX・PPTX を含む両ビルドの機能・依存対応表と固定 SHA/toolchain がある。
- [ ] 同条件の Wasm raw/gzip/Brotli と初回ロード総量・内訳を並べ、測定不能・非同等条件を明示している。
- [ ] 同一入力の成功と出力妥当性を確認し、cold/warm 処理時間と反復統計を併記している。
- [ ] メモリ baseline/peak/retained と測定範囲・限界を示し、異なる種類のメモリ指標を同列比較していない。
- [ ] 生データから集計表を再生成でき、追試に必要な環境・コマンド・入力ハッシュが揃っている。
- [ ] README/比較文書に上流と bdf.mbt の結果を併記し、現行版に対する測定日と条件を示している。

## テスト計画

- 共通機能対応表をレビューし、軽量版と全機能版の取り違えを検出する。
- 圧縮前後の復号ハッシュ一致、全 Wasm module とロード資産の計上漏れ、転送合計の一致を検証する。
- 同一の合成入力を両実装で変換し、失敗・未対応・出力不一致が統計から区別されることを確認する。
- cold/warm を別セッションで複数回実行し、時刻計測、メモリ取得不可、タイムアウトの記録を確認する。
- raw data から同じ比較表が再生成できることを確認する。

## リスク

機能差、ランタイム差、GC、フォント、計測API、ブラウザー最適化、共有プロセスが比較を歪める可能性がある。
公平な測定経路が確定しない場合は阻害を記録し、具体的な計測基盤の実装 issue に分離する。
数値を推測で補完しない。
