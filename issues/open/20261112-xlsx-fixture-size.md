# XLSX 互換テストのフィクスチャ容量を削減する

## 背景

`compat/xlsx` には、upstream の Go 実装と MoonBit 実装の互換性を確認するためのフィクスチャが多数保存されている。

現状、入力 XLSX や Go 実装が生成した期待 BDF が Base64 文字列として JSON に埋め込まれており、`compat/xlsx` 全体のファイルサイズは約 710.7 MiB となっている。

調査した代表例では、同一の入力や期待結果が複数ケースに含まれている。

| フィクスチャ | ケース数 | 異なる入力 XLSX | 異なる期待 BDF |
| --- | ---: | ---: | ---: |
| `conditional-top.json` | 257 | 153 | 43 |
| `simple-picture.json` | 48 | 48 | 48 |

また、`generate_render_test.go` には固定 seed で入力を生成する処理が既にある。一方、同じ入力を将来も再生成できるか、生成時間が実用的かは未検証である。

## 目的

既存の互換性検証を維持しながら、リポジトリに保存する XLSX 互換フィクスチャの容量を削減する。

ケース数を減らすことを目的とせず、保存形式、重複、圧縮、再生成の可能性を計測に基づいて検討する。

## 対象

- `compat/xlsx` の互換性検証用フィクスチャ
- フィクスチャの生成・読み込み・検証に必要なスクリプト
- 関連する CI 設定および開発者向けドキュメント

## 対象外

- upstream の Go 実装や MoonBit の XLSX 変換仕様の変更
- テストケースを単純に削除して容量を減らすこと
- Git 履歴の書き換え
- ファジング基盤の導入

## 作業内容

### 1. 現状を計測する

- [ ] `compat/xlsx` のフィクスチャについて、ファイル別・用途別のサイズとケース数を集計する。
- [ ] 入力 XLSX と期待 BDF それぞれについて、ファイル内およびファイル間の完全一致重複を集計する。
- [ ] Base64 の復号、重複排除、圧縮による削減効果を測定する。
- [ ] 通常の検証にかかる時間と、可能であればメモリ使用量を記録する。
- [ ] 計測に使用したコミット、コマンド、環境、結果を記録する。

全体の削減率は、計測するまで確定値として扱わない。

### 2. 保存方式を比較する

少なくとも次の方式について、容量、読み込み時間、変更差分の見やすさ、実装・運用の複雑さを比較する。

- 現行 JSON を圧縮する。
- 入力と期待結果をバイナリとして保存し、ケースから参照する。
- 内容ハッシュを用いて同一データを重複排除する。
- 生成可能な入力を必要に応じて再生成する。

`conditional-top.json` と `simple-picture.json` を代表ケースとして扱い、重複が多い場合と少ない場合の両方を検証する。

ハッシュを使用する場合は、データの識別や整合性確認に使う。期待結果の検証をハッシュ比較だけに置き換えず、既存の比較が確認している内容と差分の調査可能性を維持する。

### 3. 移行方法を試作する

- [ ] 比較結果を基に方式を選択し、その理由とトレードオフを記録する。
- [ ] 代表フィクスチャの変換と読み込みを試作する。
- [ ] 旧形式と新形式を照合し、各ケースの入力、期待結果、オプション、警告、順序および識別子を維持できることを確認する。
- [ ] 破損、参照先の欠落、不正なハッシュなどを検出できることを確認する。
- [ ] `verify-render.mjs` の既存のシャード分割と、ケースの重複・欠落を検出する仕組みを維持する。

### 4. 効果のある範囲へ適用する

- [ ] 試作結果を踏まえ、容量削減に効果があり、保守可能な範囲に適用する。
- [ ] 現行 verifier が行う入力、警告、BDF のメタデータ・ビュー・テーブル・各 part の比較を維持する。
- [ ] 実ファイルや過去の不具合を再現するケースを維持する。
- [ ] フィクスチャの生成、更新、検証方法をドキュメント化する。
- [ ] 変更前後の容量、検証時間、メモリ使用量を比較して記録する。

入力の再生成に切り替える場合は、upstream のコミット、生成器、必要な依存環境を固定し、保存済みケースとの対応と再現性を確認する。固定 seed の存在だけを再現性の証明としない。

## 受け入れ条件

- [ ] 対象フィクスチャの変更前後のサイズと削減率が記録されている。
- [ ] 対象ケースが削除・欠落・重複していないことを確認できる。
- [ ] 移行対象の各ケースについて、旧形式から復元した入力と期待結果、および各種オプション・警告が新形式と一致する。
- [ ] 既存の互換性検証で比較していた内容を維持している。
- [ ] シャード実行時に、全ケースの実行と重複・欠落を引き続き確認できる。
- [ ] 破損または参照先の欠落がある場合、テストが明示的に失敗する。
- [ ] 開発者がフィクスチャを生成・更新・検証する手順が記載されている。
- [ ] 変更前後のテスト時間を記録し、増加がある場合は理由と採否を説明している。
- [ ] Git 履歴の書き換えは行っていない。

## テスト計画

1. 移行前後のフィクスチャを全件照合し、入力 bytes、期待 BDF bytes、オプション、警告、ケースの識別子を比較する。
2. 変更対象の個別 verifier を実行する。
3. `npm run test:xlsx-compat` を実行する。
4. `verify-render.mjs` の全ケース列挙・シャード実行・実行集合の検証を確認する。
5. 欠落・破損したフィクスチャを用いた異常系を確認する。
6. 必要に応じて既存 CI 相当のテストを実行する。

テストを実行できなかった場合は、その理由と未実行の範囲を記録する。

## 補足

現在のファイルを小さくしても、過去の大きなファイルは Git 履歴に残る。通常の変更による作業ツリーの容量削減と、履歴を書き換えて過去の容量まで削減することは別の作業として扱う。
